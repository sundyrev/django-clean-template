# Django Clean Template

**Important**: Before running the project, you must configure SSL and generate certificates for HTTPS support. See [Configuring HTTPS for Production](#configuring-https-for-production) for instructions on setting up SSL certificates (e.g., using Let's Encrypt or self-signed certificates).

A clean and production-ready Django project template that supports both local deployment (via Systemd, Nginx, and Gunicorn with Unix sockets) and containerized deployment (via Docker with TCP ports). It includes modern tools like `uv` for dependency management and is designed to help you start development quickly.

## Features

- Django 5.0 (latest stable version at the time of writing)
- Python 3.12
- Dependency management with `uv` (a fast alternative to `pip`)
- Gunicorn with Unix sockets for local deployment and TCP ports for Docker
- Nginx as a reverse proxy for serving static and media files
- PostgreSQL 13+ support
- Redis 7+ for caching (with basic configuration)
- Docker and Docker Compose for containerized deployment
- Split settings for `local` and `production` environments with `.env` files
- Jinja2 templating support alongside Django templates
- Code quality tools including `ruff` for linting Python code and `djlint` for linting and formatting Jinja2 templates
- Authentication with `django-allauth` (including MFA support)
- Pre-configured logging with separate log files for Django, Gunicorn, and Nginx
- Test coverage measurement with `coverage` and `.coveragerc` for precise code coverage reports

## Limitations

- Requires PostgreSQL (13 or higher); no MySQL support
- Configuration via environment variables; no Apache/mod_wsgi support
- Docker deployment uses TCP ports for simplicity; Unix sockets require additional setup

## Prerequisites

- **Python 3.12+**: Ensure it is installed and accessible as `python3`.
- **Git**: For cloning the repository.
- **sudo privileges**: Needed for installing system packages and configuring services.
- **PostgreSQL 13+**: Required database (installed by `install.sh` for local setup).
- **Docker and Docker Compose** (optional, for containerized deployment):

## Quick Start

1. Clone the repository:

   ```zsh
   git clone https://github.com/sundyrev/django-clean-template.git
   cd django-clean-template
   ```

2. Configure SSL certificates (see [Configuring HTTPS for Production](#configuring-https-for-production)).

3. Run the installation script:

   - For local development:

     ```zsh
     mkdir <project_name>
     cd <project_name>
     uv python pin 3.12
     ./install.sh
     ```

   - For production environment:
     ```zsh
     mkdir <project_name>
     cd <project_name>
     ./install.sh
     ```

   Follow the prompts to enter the domain name, project name, and environment (development or production).

4. Apply database migrations:

   ```zsh
   source env/bin/activate
   cd <project_name>
   python manage.py migrate
   ```

5. For local deployment, start Gunicorn:

   ```zsh
   ./gunicorn.sh --project <project_name> --dev
   ```

   Check Gunicorn status:

   ```zsh
   sudo systemctl status <project_name>.gunicorn@local.service
   ```

   Access the app:

   - Development: Open `https://<project_domain>/admin` (requires HTTPS setup).
   - Production: Open `https://<project_domain>/admin` (requires HTTPS setup).

6. For Docker deployment, build and run:

   ```zsh
   docker-compose up --build -d
   ```

   Access the app: Open `https://localhost/admin` (requires SSL certificates mounted in Docker).

## Detailed Installation

1. **Clone the repository:**

   ```zsh
   git clone https://github.com/sundyrev/django-clean-template.git
   cd django-clean-template
   ```

2. **Configure SSL certificates:**

   Follow the instructions in [Configuring HTTPS for Production](#configuring-https-for-production) to generate or obtain SSL certificates and place them in the `ssl/` directory.

3. **Run the installation script:**

   ```zsh
   sudo ./install.sh
   ```

   - You will be prompted to enter:
     - **Domain name**: e.g., `example.com` (without protocol). Ensure it points to your server's IP in DNS or add to `/etc/hosts` for local testing:
       ```plaintext
       127.0.0.1 example.com
       ```
     - **Project name**: e.g., `myproject`.
     - **Environment**: Choose `1` for Development (local) or `2` for Production.
   - The script will:
     - Install system dependencies (Python, PostgreSQL, Nginx, etc.).
     - Create the project structure.
     - Set up a Python virtual environment with `uv`.
     - Configure PostgreSQL, Gunicorn, and Nginx.
     - Generate a secure `SECRET_KEY` and update `.env` files.

4. **Configure environment variables:**

   - Edit `conf/env_vars/local.env` or `conf/env_vars/production.env` as needed:
     - Update `SECRET_KEY` (auto-generated by the script).
     - Adjust `DATABASE_URL` if using a custom database.
     - Set `EMAIL_*` settings for production email (e.g., SMTP credentials).

## Configuring HTTPS for Production

To enable HTTPS, obtain an SSL certificate (e.g., using Let's Encrypt) or use self-signed certificates for testing:

1. **Using Let's Encrypt**:

   Install Certbot:

   ```zsh
   sudo apt install certbot python3-certbot-nginx
   ```

   Run Certbot to configure Nginx:

   ```zsh
   sudo certbot --nginx -d <project_domain>
   ```

   Follow the prompts to set up the certificate. Certbot will update your Nginx configuration (`conf/nginx/local/<project_name>.conf`) to include SSL settings.

2. **Using Self-Signed Certificates (for testing)**:

   Generate certificates:

   ```zsh
   sudo mkdir -p <project_path>/ssl
   sudo openssl req -x509 -nodes -days 365 -newkey rsa:2048 -keyout <project_path>/ssl/cert.key -out <project_path>/ssl/cert.crt
   ```

   Ensure the certificates are placed in `<project_path>/ssl/` and have correct permissions (set by `install.sh`).

3. Verify HTTPS:

   ```zsh
   curl -I https://<project_domain>
   ```

For Docker deployments, mount the SSL certificates in `docker-compose.yml`:

```yaml
volumes:
  - ./ssl/cert.crt:/etc/nginx/ssl/cert.crt:ro
  - ./ssl/cert.key:/etc/nginx/ssl/cert.key:ro
```

Alternatively, use a reverse proxy like Traefik or Caddy for automated SSL in Docker.

**Note**: The Nginx configuration includes a redirect from HTTP to HTTPS. Ensure certificates are in place before starting Nginx. Uncomment the HSTS headers in `conf/nginx/docker/<project_name>.conf` or `conf/nginx/local/<project_name>.conf` only after verifying HTTPS works.

## Configuring django-allauth

The project includes `django-allauth` for authentication with MFA support. To enable social authentication or customize settings:

1. Update `config/settings/production.py`:

   ```python
   ACCOUNT_EMAIL_VERIFICATION = "mandatory"  # Require email verification
   SOCIALACCOUNT_PROVIDERS = {
       'google': {
           'APP': {
               'client_id': 'your-client-id',
               'secret': 'your-secret',
           }
       }
   }
   ```

2. Run migrations for `allauth`:

   ```zsh
   python manage.py migrate
   ```

3. Configure the Site in Django admin (`/admin/sites/site/`) to match your domain.

See [django-allauth documentation](https://django-allauth.readthedocs.io/) for more options.

## Dependency Management

The project uses `uv` for fast and reliable dependency management, offering significant performance improvements over `pip`. Dependencies are defined in `.in` files and compiled to `.txt` files.

- **Add a new dependency**:

  ```zsh
  echo "new-package>=1.0.0" >> project_name/requirements/local.in
  uv pip compile project_name/requirements/local.in --no-emit-options --output-file project_name/requirements/local.txt
  uv pip sync project_name/requirements/local.txt
  ```

- **Update an existing dependency**:

  ```zsh
  uv pip compile --upgrade project_name/requirements/local.in --no-emit-options --output-file project_name/requirements/local.txt
  uv pip sync project_name/requirements/local.txt
  ```

### Helper Scripts for Local Deployment

- **`gunicorn.sh`**:

  - Manages the Gunicorn service for either `local` or `production` environments, allowing quick switching between them.
  - Supports two parameters:
    - `--project <project_name>`: Specifies the project name (e.g., `--project nowknow`). If not provided, prompts for the project name and path.
    - `--dev`: Optional flag to activate the `local` environment. If omitted, the `production` environment is activated by default.
  - Automatically stops the opposite environment (e.g., stops `production` when starting `local`) and syncs environment-specific dependencies using `uv pip sync`.
  - If a corresponding environment variable (e.g., `PROJECT_NAME_PATH`) is set, it uses that path; otherwise, it prompts for the path.
  - Usage:

    ```zsh
    ./gunicorn.sh --project nowknow --dev  # Start local environment
    ./gunicorn.sh --project nowknow        # Start production environment
    ```

    Or without parameters:

    ```zsh
    ./gunicorn.sh
    ```

- **`runserver.sh`**:

  - Starts the Django development server for quick testing in the `local` environment.
  - Supports the `--project` parameter to specify the project name (e.g., `--project <project_name>`). If not provided, it prompts for the project name and path.
  - If a corresponding environment variable (e.g., `PROJECT_NAME_PATH`) is set, it uses that path; otherwise, it prompts for the path.
  - Usage:

    ```zsh
    ./runserver.sh --project nowknow
    ```

    Or without parameters:

    ```zsh
    ./runserver.sh
    ```

- **Setting up environment variables for helper scripts**:

  To streamline usage of `gunicorn.sh` and `runserver.sh`, you can set an environment variable for your project's path. For example, to set the path for a project named `<project_name>`:

  ```zsh
  echo 'export PROJECT_NAME_PATH="$HOME/projects/<project_directory>"' >> ~/.zshrc
  source ~/.zshrc
  ```

  This ensures the `PROJECT_NAME_PATH` variable is available in every new terminal session, allowing the scripts to automatically use the specified path when `--project <project_name>` is provided. Replace `<project_directory>` with your actual project directory name.

## Why Sockets Locally and TCP in Docker?

- **Local (Unix Sockets)**: Faster for local setups because they communicate directly on the same machine.
- **Docker (TCP Ports)**: Standard for containers, as sockets are harder to share between containers.

This intentional split allows flexibility: local development can skip Docker builds, while Docker provides a portable production-like environment. For consistency across all environments, consider using TCP ports everywhere (see [Best Practices](#best-practices)).

## Best Practices

- **Consistency**: For larger projects or team collaboration, use TCP ports (`127.0.0.1:8000` locally, `0.0.0.0:8000` in Docker) everywhere to avoid configuration differences.
- **Security**: Update `production.env` with a strong `SECRET_KEY`, enable HTTPS (required), and store SSL certificates securely (see [Configuring HTTPS for Production](#configuring-https-for-production)).
- **Redis Configuration**: The provided `conf/redis/redis.conf` is a basic template for development. Before production, adjust settings like `maxmemory`, uncomment and set `requirepass` for security, and review other parameters based on your workload.
- **django-allauth**: Requires `allauth.account.middleware.AccountMiddleware` in `MIDDLEWARE` (included in `base.py`). Configure additional settings (e.g., social auth) in `settings/production.py` if needed.
- **Monitoring**: Integrate Sentry (included in `production.in`) by setting `SENTRY_DSN` in `production.env`.
- **Test Coverage**: Use `coverage` to measure test coverage and ensure high code quality. Run tests with coverage and generate a detailed report:
  ```zsh
  coverage run <project_name>/manage.py test config.tests
  coverage report -m
  ```

## Troubleshooting

- **Gunicorn fails to start**:

  - Check logs:
    ```zsh
    sudo journalctl -u <project_name>.gunicorn@local.service
    sudo journalctl -u <project_name>.gunicorn@production.service
    ```

- **Nginx errors**:

  - Review logs:
    ```zsh
    cat log/nginx/error.log
    docker-compose logs nginx  # For Docker
    ```

- **Database issues**:

  - Verify `DATABASE_URL` in `conf/env_vars/<environment>.env` and ensure PostgreSQL is running:
    ```zsh
    sudo systemctl status postgresql
    ```

- **Redis fails to start**:

  - Check logs:
    ```zsh
    docker-compose logs redis
    ```
  - Ensure `conf/redis/redis.conf` syntax is valid (comments on separate lines).

- **Port 80/443 conflict (Nginx fails to start)**:

  - Error: `bind() to 0.0.0.0:80 failed (98: Address already in use)`.
  - Cause: Another service (e.g., Apache, another Nginx instance, or a Docker container) is using port 80 or 443.
  - Solution:
    ```zsh
    sudo netstat -tulnp | grep :80
    # OR
    sudo lsof -i :80
    sudo kill -9 <PID>  # Replace <PID> with the process ID
    sudo systemctl restart nginx
    ```
    If using Docker, stop conflicting containers:
    ```zsh
    docker-compose ps -a
    docker-compose stop <service_name>
    ```

- **Django returns 502 Bad Gateway**:

  - Cause: Gunicorn is not running or the socket (`/run/<project_name>.gunicorn.sock`) is inaccessible.
  - Solution:
    ```zsh
    sudo systemctl status <project_name>.gunicorn@local.service
    sudo systemctl restart <project_name>.gunicorn@local.service
    sudo ls -l /run/<project_name>.gunicorn.sock
    ```

- **Environment variables not loaded**:
  - Cause: Incorrect `SECRET_KEY` or `ALLOWED_HOSTS` in `conf/env_vars/<environment>.env`.
  - Solution:
    ```zsh
    cat conf/env_vars/<environment>.env
    ```
    Ensure `ALLOWED_HOSTS` includes your domain (e.g., `example.com,127.0.0.1`) and `SECRET_KEY` is set.

## Cleanup

To stop and remove the project, use the provided `delete.sh` script or manual commands. The `delete.sh` script is designed to safely and completely remove all project-related resources, including files, services, and optionally the database, with safeguards to prevent accidental deletion.

- **`delete.sh`**:

  - **Purpose**: Stops and removes all project-related services, files, and Docker containers, with options for local development and production cleanup.
  - **Features**:
    - **Double Confirmation**: Prompts for the project name twice to prevent typos.
    - **Local Mode**: Use the `--local` flag to skip Nginx cleanup for local development projects.
    - **Database Cleanup**: Optionally removes the PostgreSQL database (`<project_name>_db`) and user (`<project_name>_user`) with a separate confirmation.
    - **Virtual Environment**: Removes the production virtual environment (`/opt/<project_name>`).
    - **Logging**: Saves all operations to `/var/log/delete-<project_name>-<timestamp>.log` for auditing (e.g., `/var/log/delete-myproject-2025-04-12-143022.log`).
  - **Usage**:

    - For local development (skips system services):
      ```zsh
      sudo ./delete.sh --local
      ```
    - For full cleanup (local or production):
      ```zsh
      sudo ./delete.sh
      ```
    - **Example Prompts**:
      ```plaintext
      [1/2] Project name: myproject
      [2/2] Confirm project name: myproject
      [3/3] Project path: ~/django-project
      Are you sure you want to delete the project myproject at /home/user/django-project? [y/N]: y
      Do you want to delete the PostgreSQL database myproject_db and user myproject_user? [y/N]: y
      ```
    - **Output**: Logs are saved to `/var/log/delete-<project_name>-<timestamp>.log`, and a success message confirms deletion.

  - **Safety**:
    - Prevents deletion of the script's own directory.
    - Requires explicit confirmation (`y` or `Y`) for project and database removal.
    - Checks for the existence of files and services before attempting deletion.
    - Logs all actions for troubleshooting or auditing.

- **Manual Cleanup (Alternative)**:

  - **Local**:

    ```zsh
    sudo systemctl stop <project_name>.gunicorn@local.service
    sudo systemctl stop <project_name>.gunicorn@production.service
    sudo systemctl disable <project_name>.gunicorn@local.service
    sudo systemctl disable <project_name>.gunicorn@production.service
    sudo rm /etc/systemd/system/<project_name>.gunicorn@.*
    sudo systemctl daemon-reload
    sudo systemctl restart nginx
    rm -rf <project_directory>
    ```

  - **Docker**:

    ```zsh
    docker-compose down -v
    ```

  - **Database** (if not using `delete.sh`):

    ```zsh
    sudo -u postgres psql
    REVOKE ALL PRIVILEGES ON DATABASE <project_name>_db FROM <project_name>_user;
    ALTER ROLE <project_name>_user RESET client_encoding;
    ALTER ROLE <project_name>_user RESET default_transaction_isolation;
    ALTER ROLE <project_name>_user RESET timezone;
    DROP DATABASE IF EXISTS <project_name>_db;
    DROP ROLE IF EXISTS <project_name>_user;
    \q
    ```
